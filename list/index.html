  • Billion-Token Scale Trace Analysis: Jev vs LLMs

    Bryan Lee, appliedcompute.com, added Sep 24

    Bryan Lee shows how Applied Compute finds recurring agent failures across long traces, builds a taxonomy with frontier models, then uses Jev as a cheap and well-calibrated classifier for annotation at scale.

    My notes

    Fifty GPT-5.2 traces produced a taxonomy of 14 labels, including 12 agent failure modes and two other outcomes.

    My notes

  • Why do CPUs have multiple cache levels?

    Fabian Giesen (ryg), fgiesen.wordpress.com, added Sep 5

    Fabian Giesen on why CPUs have several cache levels instead of one big one, told through a 1960s paper office where your desk is L1 and the basement archive is L3.

    My notes

    Each level up is bigger, slower, denser and cheaper per bit. A bigger L1 is physically farther away, which makes it slower.

    Private L1 needs no coordination. L2 absorbs most bus traffic on the core’s behalf. Shared L3 must be coordinated through the bus.

    L1 is split into instruction and data caches. Instruction fetch alone can run about 50 GB/s per core at 3 GHz on a Core i7.

    Chips are floor plans with real wires. At 4 GHz a signal covers about 18.7 mm per cycle one way, shorter than a Skylake die.

  • How prompt caching works - Paged Attention and Automatic Prefix Caching plus practical tips

    Sankalp, sankalp.bearblog.dev, added Sep 3

    Sankalp’s writeup of how prompt caching actually works at providers, from the practical tips (stable prefix, append-only context) down to vLLM’s paged attention and chained block hashes.

    My notes

    Caching is per content, not per conversation. A system prompt with no user data is a shared prefix across every user on your key.

    Keep context append-only and serialize deterministically. Truncating old tool outputs or reordering JSON keys breaks the prefix.

    vLLM stores KV in 16-token blocks hashed with the parent block’s hash. One matching hash proves the entire prefix matches.

    Hits cut input price up to 10x. Anthropic bills extra for cache writes, OpenAI does not. prompt_cache_key is only a routing hint.

  • How speculative decoding makes LLMs go brrr

    Leonie Monigatti, leoniemonigatti.com, added Sep 2

    Leonie Monigatti’s study notes on speculative decoding: the draft-and-verify math that gives free speedups with no quality loss, then Medusa, EAGLE, DFlash and DSpark as answers to the drafter problem.

    My notes

    Draft 3 to 12 tokens with a cheap model, verify them in one target pass. Rejection sampling keeps the exact target distribution.

    The speedup is idle compute: decoding is memory-bound at low batch. Latency per token is (draft + verify time) / accepted length.

    Reported speedups: separate draft model 2-3x, Medusa-2 2.3-3.6x, EAGLE-3 up to 6.5x, DFlash over 6x at best and 4-5x on average.

    At high batch and short context the target is compute-bound and speculation can cut throughput. It is a flag in vLLM and SGLang.

  • Every Token Gets a Weight

    Zhoutong Fu, zhoutongfu.github.io, added Aug 13

    Zhoutong Fu’s tour of LLM RL updates from PPO to on-policy distillation, read through one lens: every method is a rule for how much a sampled token’s log-prob update should count.

    My notes

    The actor loss is a token log-prob times a weight. Reward, ratio, normalization and teacher gates all meet at that one multiplier.

    GRPO gives every token in a response the same advantage. The right algebra step and the detour get the same push.

    PPO’s ratio corrects data reuse, not reward. Rollout vs trainer log-prob drift is a second ratio to clip or mask (TIS, IcePop).

    Teacher signals need a trust gate. SRPO uses SDPO on failed samples only, RLSD lets reward set the sign and the teacher the size.

  • Queues Don’t Fix Overload

    Fred Hebert, ferd.ca, added Jul 29

    Fred Hebert’s 2014 rant on why a queue in front of an overloaded system is a bigger bucket, not a fix. Prolonged overload has one hard limit somewhere, and you have to pick what gives.

    My notes

    A queue as a buffer makes failures rarer and bigger. More workers or a persistent queue only defer the same crash.

    Two choices when the sink overflows: block callers (back-pressure) or drop work (load-shedding). Inaction picks the crash for you.

    Step 1: find the real bottleneck. Step 2: ask it for permission before piling more in. Slowness was already the canary.

    My notes

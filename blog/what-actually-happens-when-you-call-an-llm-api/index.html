What Actually Happens When You Call an LLM API

Aadesh IngleAUG 09 · 20254 Min

That model is fine right up until production, where it explains none of the things that actually happen to you: the 429s, the latency that varies for identical prompts, the bill that doesn't match intuition. The version that survives contact with production looks more like:

The conclusion hiding in that list, and the single most useful sentence I can offer about LLM infrastructure: these are distributed systems first and neural networks second. The transformer is one stage in a pipeline that is mostly ordinary, hard, unglamorous systems engineering. Which means most "model problems" you'll debug are actually systems problems wearing a model costume.

A walk through the stages that matter.

The gateway: where 429 actually lives

A 429 feels like "the model is overloaded." It almost never means that. It means an accountant said no: you exceeded requests per minute, or tokens per minute, or concurrent sessions, whichever ledger you hit first. Providers keep separate quotas per model, per org, sometimes per region. Knowing which ledger rejected you changes the fix entirely. Request-rate limits want batching or spacing; token-rate limits want shorter prompts or a different model tier; concurrency limits want a queue on your side.

The tokenizer: where the bill is decided

The model never sees your text. It sees integers, and you're billed per integer. This is worth internalizing because compression varies wildly: prose tokenizes efficiently, code less so, and JSON with verbose keys is close to the worst case. The same information as structured output can cost meaningfully more than as prose. When a bill surprises you, the tokenizer is usually where the surprise was manufactured.

The router: why "the model" isn't one thing

The endpoint name you call is a label, not a machine. Behind it sits routing: requests classified and dispatched across clusters, hardware tiers, sometimes model variants, balancing quality against cost against load. This is one reason identical requests at different hours behave differently, and why a provider's behavior can shift without any announced model change. If your system silently depends on behavioral quirks, it depends on routing decisions you can't see. Evals, not vibes, are how you notice when the floor moves.

The queue: why evening latency doubles

GPU serving is queue-sensitive in the way all heavily utilized systems are: near saturation, small increases in load produce large increases in waiting. That's not an AI fact, it's queueing theory, and it's the answer to the six-o'clock question. The provider's clusters run hottest at peak hours; your request waits longer for a batch slot; "the model got slower" is three queues deep and none of them is the model.

The practical consequences for anyone integrating:

  • Log latency in segments, not as one number. Time to first token and time between tokens have different causes and different fixes.
  • Expect variance, and design timeouts around the tail you observe, not the average you were promised.
  • Same prompt, different latency is normal, not a bug to file.

Prefill and decode: the two-act structure

Your prompt is processed in one parallel pass (prefill), which is fast per token. Then the response is generated one token at a time (decode), each token depending on the last. That sequential loop is the part nothing can parallelize away, and it dominates end-to-end latency. The visible symptom: long outputs feel disproportionately slow, because they are. Output length is the latency lever most teams never think to pull.

This split also explains streaming. It isn't just a UX flourish; it's the honest shape of the computation. Tokens exist one at a time, so showing them one at a time costs nothing and hides the sequential wait.

What I actually changed after internalizing this

Less than you'd think, and it mattered more than you'd think. We cap output lengths everywhere a long answer isn't the product. We log provider, model version, and segmented latency on every request. We treat 429s as quota engineering, not capacity mysticism. And when latency drifts, we ask the queueing question before the model question, because that's the base rate telling us where to look.

None of this required understanding attention math. It required taking seriously that there's a whole building between you and the matrix multiplications, and the building has opening hours.

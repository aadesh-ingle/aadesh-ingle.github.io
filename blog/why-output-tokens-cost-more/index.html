Why Output Tokens Cost More Than Input

Aadesh IngleFEB 15 · 20257 Min

Look at any LLM provider's pricing page and the same asymmetry appears: output tokens cost several times what input tokens do. Teams tend to shrug at this as pricing-page arbitrariness. It isn't. It's the economics of how inference physically works, and once you see the mechanism, several "best practices" stop being folklore and start being obvious.

One pass in, one token at a time out

When your request arrives, the prompt is processed in a single parallel pass. Every input token flows through the model together, the GPU does what GPUs love (large batched matrix work), and the per-token cost is comparatively small. This phase is called prefill.

Then generation starts, and the physics change. Each output token depends on every token before it, so the model produces them strictly one at a time: generate a token, append it, generate the next. No amount of hardware parallelizes away that loop, because the dependency is in the math, not the implementation. Sequential work on hardware built for parallel work is expensive work. That's the asymmetry, the whole thing.

A side effect worth knowing: the model caches intermediate state (the attention keys and values) for every token in the conversation so far, and that cache lives in GPU memory for the duration of your request. Long contexts are therefore less a compute problem than a memory-occupancy problem. You're not just buying computation; you're renting space on the most expensive real estate in the datacenter for as long as your generation runs.

What providers do about it, and why you see the side effects

The provider's whole serving game is keeping GPUs busy despite the sequential loop. The main trick is continuous batching: interleaving the decode steps of many users' requests so the hardware never idles between tokens. It works well, and you feel its consequences without knowing their name: token-to-token pacing that varies with load, latency that's queue-shaped at peak hours, throughput that's excellent on average and uneven in the particulars.

Prompt caching is the other lever. If your requests share a long prefix (a system prompt, a tool schema, a pile of context), providers can reuse the computed state instead of re-running prefill every time. The right mental model is a CDN for attention: the static part of your request gets served from cache, and only the dynamic part costs full price. Pricing pages reflect this directly with discounted cached-input rates.

What this should change in how you build

Practical consequences, in the order they've saved me money:

  1. Cap output length anywhere prose isn't the product. Output is the expensive direction and the slow one. An extraction task that returns a paragraph of polite framing around the JSON is paying premium rates for filler. Asking for terseness is a cost optimization, not a style preference.
  2. Structure long prompts for cache hits. Stable prefix first (system prompt, schemas, examples), volatile content last. A reordered prompt that breaks prefix-sharing silently turns cached rates back into full rates.
  3. Don't pad max-token limits "to be safe." Generous ceilings invite generous answers, and some serving stacks make scheduling decisions off your declared maximum. Set limits near what correct output actually needs.
  4. Watch the verbosity of structured output. Schema design is cost design: key names are tokens, nesting is tokens, and a chatty schema multiplies across every request you'll ever make.
  5. Stream by default for anything user-facing. It doesn't make generation faster, but it makes the sequential wait honest, and perceived latency is the latency users act on.

The operating rule is: spend output tokens only where the answer itself is the product. Everywhere else, terseness, cache-friendly prompt order, and tight ceilings are not polish. They are infrastructure controls.

Two questions to test the intuition

I've started asking versions of these when working with engineers new to LLM systems, because the answers reveal whether the mental model has landed:

Why can a huge context window be mostly a memory problem rather than a compute problem? Because the cached state for every context token has to sit in GPU memory for your entire request, displacing other work the hardware could be doing. The cost isn't processing the tokens once; it's housing them for the duration.

Why might raising your max-output setting affect latency even when responses stop early? Because the limit you declare can shape scheduling and memory reservation before a single token is generated. The ceiling is part of the request's footprint, whether or not the answer reaches it.

If those two answers feel natural, the pricing page asymmetry stops looking like a vendor decision and starts looking like what it is: a fairly direct invoice for the shape of the computation. Input is a crowd through a wide door. Output is a queue through a turnstile, one click at a time, while the meter runs.

Stop Being the Thing Inside the Loop

Aadesh IngleJUN 10 · 2026

I keep having a version of the same conversation. Someone describes their agent setup, and what they have is a cron job that prompts a model every hour. Someone else has a retry wrapper. Someone else has the model calling tools until it announces it's finished. All three call it an agent loop, and all three mean different things, because the word has been redefined roughly every year since 2022.

Most of those setups reduce to this:

That's repeated prompting. A loop, in the sense that actually matters in production, is a control system. It reads state, decides an action, executes it, checks the result against something that isn't the model's own opinion, and uses that check to change what happens next. The checking part is the whole game, and it's the part most setups skip.

One word, five generations

It helps to see how the meaning drifted, because each generation kept the name and changed the contents.

ReAct gave us the think-act-observe cycle inside a single model call. AutoGPT wrapped a goal around it and promptly demonstrated the failure mode the rest of the decade would be spent fixing: agents that search, then search again, then search again, looping without progressing. The ralph pattern flipped the emphasis from cleverness to state, the same prompt fired repeatedly at a fixed set of files that accumulate progress. The productized loops that followed made one small change that I think matters more than anything else on that list: done stopped being something the model declares and became something a validator decides. And the current generation stacks loops on loops, supervisors scheduling research workers, coding workers, review workers.

Five meanings, one word. No wonder the conversations go sideways.

What a loop actually contains

Strip away the branding and every loop that works has the same four parts.

The human writes intent and stopping behavior, once, up front. Not just the goal but the exit: stop when tests pass, stop when the PR is open, stop after thirty iterations no matter what.

The controller prompts the agent each tick. This is plain code, not a model. It owns the schedule, the budget, and the decision to continue.

The agent session does the work: reads the issue, edits the code, runs the tools, touches GitHub or Slack or the database.

The feedback gate checks the work. Tests, lint, a validator model, a metric, a human. The gate's verdict, not the agent's self-assessment, decides what happens next.

The line that separates this from repeated prompting is evaluate. The verdict flows back into state, so iteration twelve behaves differently because of what iteration eleven learned. Remove that line and you have a while-true wrapped around a stranger.

I wrote before about moving negotiation policy out of the prompt and into code. This is the same instinct one level up. The model drafts; deterministic code decides whether the draft counts. A model grading its own homework will eventually give itself an A it didn't earn, and in a loop that runs unattended, "eventually" arrives fast.

The other non-negotiable is resumability. A useful loop survives a crash, a context compaction, a browser refresh, and a human approval delay. If progress lives only in the chat transcript, the controller is you. Durable state is what lets the loop become software instead of a ritual you perform manually.

Not just cron, and not just context

Two objections come up every time, so let me take them head on.

"Isn't this just cron?" No. Cron is the schedule, one ingredient. The loop body contains a model that reads current state, decides the next action, does it, checks it, and chooses whether to continue. A schedule that fires a static prompt every hour makes the same decision every hour. A loop makes a different decision every tick because the state moved.

"Can't the context window hold the state?" Not for anything real. Iteration 27 found the bug. Iteration 28 fixed it. Iteration 29 watched the tests fail anyway. That history has to survive restarts, crashes, and context compaction, which means it lives outside the model: files in the repo, a task list, artifacts, checkpoints. The ralph insight, durable state as the anchor rather than conversation history, is the one I'd keep if I could only keep one.

The three limits that make it production

Every loop that has run unattended near real money has the same three guardrails, and every demo that melted down was missing at least one:

  1. An iteration cap. Thirty steps, then stop, no appeals. Prevents the runaway.
  2. No-progress detection. If the diff hasn't changed and the test count hasn't moved in N iterations, the loop is spinning, not working. Stop it. This is the AutoGPT lesson, paid for in 2023 and still being re-learned.
  3. A token and dollar ceiling. A five dollar task should not be able to become a five hundred dollar bill because the gate kept saying "not yet." Track tokens, cost, and wall-clock per run, and kill at the ceiling.

None of these are clever. That's the point. They're the boring rails that let you stop watching.

The loop is not the asset

The part worth underlining: after all the architecture talk, the loop itself is maybe a hundred lines of unremarkable code. What makes it worth anything is what the agent can do inside it: search, edit, run tests, query the database, open a PR. The skills.

A CPU with no programs does nothing. A loop with no skills is a while-true around a very expensive random number generator. The teams I see getting compounding value aren't the ones with the most elaborate orchestration diagrams; they're the ones with a library of sharp, named, tested capabilities that any loop can pick up. The orchestration layer changes every six months. The skill library appreciates.

Which leads to the actual thesis, the thing I tell people at the end of that recurring conversation. Look at your own week. If you are the one re-prompting after every failure, pasting test output back into the chat, deciding whether the work is done, then you are the feedback gate, the state store, and the controller. You are the thing inside the loop. That's fine while you're learning what the gate should check. But the moment you can write the check down, write it down. Give the loop the skills, the feedback, and the hard stops, and go do something a while-true can't.

Running Two Model Providers in Production

Aadesh IngleJUN 21 · 2025

Across the client systems we run, two model providers are live in production: OpenAI's GPT series and Google's Gemini, the latter consumed through the Vertex AI SDK. One of our deployments, a call-analytics pipeline doing transcription, summarization, sentiment, and intent, runs on Vertex end to end. Others mix providers by task. I want to write down what this actually looks like, because "multi-provider" gets discussed like an architecture-diagram decision and lived like an operational discipline.

Why bother

The reasons turned out to be less romantic than resilience-architecture blog posts suggest.

Clients arrive with cloud commitments. If their world runs on GCP, meeting them there isn't a preference, it's a requirement. Different models genuinely win at different tasks, and the gap moves with every release. And when one provider has a bad day (rate limits, degraded latency, a rough deploy), being structurally able to shift traffic is the difference between an incident on their status page and an incident on yours. Not that you'll flip a switch and feel nothing; anyone selling instant failover between LLM providers is selling something. But able to move in days beats locked in for quarters.

The less obvious reason is organizational. Once a team has run two providers for real, it stops treating the model vendor as the architecture. The architecture becomes the contract: what the application gives the model, what the model is allowed to return, which side owns retries, and what evidence a run leaves behind. That contract is boring in the best way. It keeps a model swap from becoming a rewrite.

The myth of the portable prompt

I believed, going in, that prompts were roughly portable. Same instructions, swap the endpoint, tune slightly. They are not. The same prompt is a different program on a different model. Formatting habits differ. Instruction-following differs in the corners, which is exactly where production lives. Tool-calling behavior differs. The failure modes are different shapes, not different rates of the same shape: where one model truncates, the other embellishes; where one refuses, the other complies too eagerly. Treating a prompt as write-once-run-anywhere is how you ship a regression while believing you changed nothing.

What actually transfers between providers is the eval suite. The golden cases, the assertions, the judgment about what correct looks like. That's provider-agnostic by construction, because it describes your problem, not their model. Our working rule became: a provider or model swap is treated exactly like a code deploy to a critical path. It runs the full eval suite first, no matter how confident anyone feels. Confidence is precisely the danger; the new model is usually better on average, and "on average" is doing heavy lifting in that sentence.

This is the part I would design first now: not the router, the proof harness. A router without evals is just a faster way to send the same bug to a different vendor. A provider adapter earns its keep when it can answer four questions after the fact: what model served this, what prompt and tool contract did it see, what did it try to do, and how did the output compare against the same case on the other path?

Two smaller lessons

Keep the abstraction layer thin. We normalize requests, responses, and errors, and stop there. The heavyweight do-everything LLM-router frameworks average away each provider's strengths to give you a lowest-common-denominator interface. A thin shim plus per-provider prompt variants kept the strengths and cost us a little duplication, which is the right trade.

Log which provider and model version served every single request. The first time quality drifts and you can't answer "what changed?", you'll wish you had. Drift debugging without provenance is astrology.

The adapter is a quarantine layer

The adapter's job is not to pretend providers are identical. It is to keep their differences from leaking everywhere.

That means I want provider-specific code to be explicit and small: auth, endpoint shape, request construction, response parsing, retry classification, and usage accounting. Prompt variants live beside the provider, not buried inside a universal prompt builder. Tool-call parsing keeps the raw provider payload, even if the application gets a normalized object. Errors are normalized enough for operations, but the original error is still logged because "retryable provider error" is not enough when the provider changes behavior.

The mistake is building the abstraction too high. Once the adapter owns prompting, routing policy, eval interpretation, and fallback behavior, nobody can tell whether a regression came from the model, the prompt, the router, or the abstraction itself. Thin shims are less elegant. They are also easier to debug at 2 a.m.

The honest scope of all this: we consume these platforms through their APIs and SDKs. Model access, not the surrounding platform machinery. I can't tell you which provider's fine-tuning stack or vector platform is better, because that's not the layer we live at. The layer we live at taught me one durable thing: the provider is swappable, the model is swappable, and what you should actually be unwilling to rebuild is the harness around them. The evals, the logging, the contracts. That's the asset. Everything else is a vendor.

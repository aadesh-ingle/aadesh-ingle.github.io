The Model Is the Easy Part

Aadesh IngleJUN 02 · 2026
Try it yourselfProduct boundary inspector ↓

Every AI product I've worked on has had the same shape. The model call, the part everyone wants to talk about, is a few hundred lines. Everything around it is the product: permissions, guardrails, evals, observability, retries, the decision about how much of the workflow the model should even be allowed to touch. The model is the easy part. It arrives pre-trained. The rest you have to earn.

I keep meeting teams who get this backwards, and I understand why. The model is where the magic visibly lives. A founder sees a demo, the demo is astonishing, and the natural conclusion is that the work is mostly done. But a demo only has to work once, in front of a friendly audience, on input chosen by the person demoing. A product has to work on Tuesday afternoon, on the worst input of the month, while nobody is watching. The distance between those two is not closed by a better model. It's closed by engineering that has nothing to do with intelligence.

A few convictions I've collected from shipping these systems, offered with the usual caveat that they were learned by getting things wrong first.

Inspect the simulation’s limits

The sample schema and authority gates are deterministic. The downstream result is a separate observation, used only when the tool is invoked. Passing validation does not prove delivery. Real products also need permissions, idempotency, validation at each boundary, and operation-specific recovery. A confirmed result with prompt-only instructions demonstrates one successful input; it does not establish a safe product boundary.

The part no demo shows

The demo path usually has one user, one happy input, one clean output, and no downstream consequence. The production path has all the parts the demo edited out: retries, stale records, partial permissions, user corrections, provider timeouts, malformed tool arguments, and the question of who gets woken up when the system is unsure.

The uncomfortable pattern is that the answer is often "we'll add that after launch." That sounds practical until launch traffic becomes the only dataset you have and every fix is now happening under customer pressure. The outer system is not polish. It is the thing that lets you learn without breaking the workflow each time.

Start from the user's day, not the capability

The teams I've watched lose the most velocity started with a capability (an agent, a copilot, whatever the season's word is) and went looking for somewhere to put it. The question that actually opens a project is embarrassingly old-fashioned: walk me through the workflow. Show me where the friction is. Show me what gets dropped or done badly because a human is out of time. Sometimes the answer is an LLM. Sometimes it's a queue and a form. Caring about the answer more than the technology is most of the job.

Decide what the model is not allowed to decide

The most important architectural call in any system I've shipped was drawing the line between what the model proposes and what the code enforces. Anything involving money, compliance, or an irreversible action goes on the code side of the line. A prompt is a suggestion to a statistical process; it can drift with the next model version. Behavior that must never happen should be impossible, not unlikely. And "impossible" is spelled with an if statement, not with capital letters in the system prompt.

Don't fight the model longer than the evidence supports

You can't out-prompt a wrong architecture. I've tried, and I wrote up how that went on a voice product. There's a version of persistence that's really just attachment to your first design. When production keeps producing the same class of failure and your fixes keep moving the needle less each time, the system is telling you something. Low ego is operationally useful here. Being comfortable deleting your own work is a competitive advantage in a field where the first version is usually wrong in some way you couldn't have predicted.

The outer loop is the durable advantage

Model quality is a rented advantage. Whatever you have, your competitor can call the same API next quarter. What compounds is the loop around it: evals that tell you whether a change helped, observability that turns a vague complaint into a traceable failure, retrieval and context that improve with every correction, feedback from real usage flowing back into the system. Two teams with identical models will diverge completely on the strength of their outer loops. I've never seen prompt cleverness compound. I've watched eval suites do it.

The loop has to be outside the model to be useful. If the same prompt that generates the answer is also expected to enforce policy, validate tool calls, decide when to escalate, and explain whether it did a good job, the system has no independent instrument. The model can be part of judgment when the question is semantic. It should not be the only witness.

None of this is a complaint about the models, which are remarkable and getting more so. It's an argument about where the work is. When the next astonishing demo crosses your feed, the question that separates the products from the demos is unchanged: what happens around the model when it's wrong? Because in production, on a long enough timeline, it will be. And the system you built around it is the difference between an incident and a non-event.

That system is the job. The model is the easy part.
